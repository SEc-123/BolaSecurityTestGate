# 0.6.7 local task-plan consistency candidate

This iteration repairs two execution-boundary failures observed in a saved Web scan. Its verification uses disposable local fixtures only. Full Web and Android AI acceptance remain false; no saved target or APK is retried by this task.

## Endpoint plan contract

The generic test tool previously accepted a model-supplied endpoint list while selecting the target from the older persisted workflow plan. It created assets before native orchestration rejected the resulting mismatch. The same model could select another API endpoint or union extra endpoints through the upload tool.

All three execution tools now resolve the current task and run from persistence, validate the exact saved endpoint scope, and select the target from one workflow plan. They reject extra or missing endpoints, changed targets, invalid plan references, duplicate persisted entries, inconsistent plan ordering, wrong run binding, and endpoints or captures outside the declared origin before execution side effects. Caller arguments can be omitted or list the same endpoint set in a different order; caller order never changes the plan. The OTP verification heuristic no longer silently replaces a persisted target. API calls cannot change the saved vulnerability type.

The generic, upload, standalone API and native workflow runner entries repeat the same validation so direct callers cannot bypass it or supply forged transport fields. The original native action guard remains. Errors carry bounded contract metadata: a reason code, allowed endpoint IDs, saved target ID, `failure_phase: pre_action` and `action_performed: false`. The registry persists the failure for model context. These scope failures remain terminal; they do not join the selector retry path.

An explicit persisted child owns its own endpoint scope. A legacy child without a workflow plan may establish and persist a plan only inside that saved scope. An empty task scope does not grant scan-global access. A legacy upload child's missing vulnerability type can be derived only from its saved `test_file_upload` task type. A new endpoint cannot be added to an existing task by tool arguments: it needs an explicit persisted child or a consistent saved replan.

Native execution retains its existing behavior of placing the target action after the prerequisite list. This iteration validates the stored plan references and their relative ordering but does not redesign dependency inference, prerequisite execution, or authorization evidence gates.

## Selector correction

The existing bounded browser correction also applies to the explicit generic and file-upload test task types. The tool must be `browser.interact`, the error must be a missing, ambiguous or hidden selector, and both no-action markers must be present. The maximum remains two corrections per task. Scope, authentication, provider refusal, assertion, post-action and uncertain actionability failures remain terminal.

## Validation and packaging

The endpoint tests use in-memory native SQLite and a disposable loopback HTTP server, exercising the actual tool registry and native runners. They assert that rejected plans produce no requests, assets, evidence artifacts or resource-usage changes; valid plans still execute. The runtime selector tests use explicit protocol/tool fixtures and do not launch a browser or device. They are not model, browser or device acceptance.

Exact commands and results are recorded in `validation/release-0.6.7.json`. The full product/browser suite is deferred until the concurrent live scan releases its runtime. Dependencies are reused from the installed workspace, without downloads. The normal production build and source/package checksum workflow produce a local candidate archive that excludes runtime databases, configuration, captured traffic and credentials. No push, deployment or remote CI result is claimed.
