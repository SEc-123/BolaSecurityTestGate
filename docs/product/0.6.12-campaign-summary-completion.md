# 0.6.12 local campaign summary candidate

The 0.6.9 Web run `678a4808-d327-4fe3-b95b-41f0cac44e3f` persisted a useful `vulnerability_campaign_summary` artifact, but the summary task failed with `Tool task.summarize_vulnerability_campaign failed`. Its result summary correctly reported `bfla campaign summary: 0/1 child tasks completed, 0 confirmed finding(s).` Only this filtered incident metadata was supplied to the repair. No live run, target, saved account, credential or prompt was read or changed by this repair.

## Cause and contract

The handler awaited artifact persistence and then returned `ok: failed === 0`. The tool registry stored that result as a failed invocation, and the agent runtime immediately terminated the summary task. This confused a successful evidence aggregation with its unsuccessful child execution. Existing dependency-finalization coverage replaced `executeTask`, so it verified summary scheduling without exercising this handler.

After the artifact is successfully persisted, the handler now returns `ok: true`. This means only that summarization succeeded. The existing completed, failed and blocked child counts, individual child outcomes, zero confirmed findings and residual-gap wording remain unchanged. The handler never changes a child task or creates a security verdict. Artifact persistence errors still fail the invocation and summary task. No scheduler, retry, decision-budget or evidence-gate policy is changed.

The ordinary scheduler can now continue from a successful summary invocation to its completion decision. Failed children still leave the run failed; dependency-blocked children retain their existing failure finalization. A completed child without verified evidence remains inconclusive in the product view. Finishing this helper never marks an executable security test complete or establishes that an application is safe.

## Verification and limits

The new regression uses the real scheduler, tool registry and native in-memory SQLite with a loopback model protocol fixture. Against unchanged 0.6.11 source, failed-only and mixed-child cases reproduced the exact failure above while their artifacts were already persisted. After the single return-flag correction, all five cases pass:

- Failed-only, dependency-blocked-only, mixed completed/failed/blocked, and completed-without-evidence campaigns retain exact counts and residual gaps.
- Child records remain unchanged. The summary invocation completes once and its gaps reach the next model request.
- Product projection still shows zero verified completed tests and zero confirmed risks when evidence is absent.
- A SQLite trigger rejecting the summary write still produces a failed invocation and task, with no summary artifact.

The full product experience and mobile closure suites, viewer access policy, capture-addon regression, frontend/backend typechecks and normal build are recorded in `validation/release-0.6.12.json`. Product tests include the real local Chromium readiness/recovery fixtures, dependency finalization and model-context evidence gates. Mobile tests use explicit Appium/device doubles; no Android runtime or real device was started.

The two additional legacy static UI audits still fail on the same label and page-list expectations. Both failures were reproduced independently from a temporary archive of clean 0.6.11. They remain recorded failures outside this summary repair. The aggregate mobile release command requires actual device execution and was not run.

Full AI Web and Android acceptance remain false. This local fixture does not prove the real model's next completion decision or acceptance against the original target. The historical live run was not rewritten or replayed. The package includes source and normal frontend/server build output with per-file checksums; its source tree must match the final local commit. Existing dependencies were reused without installing or downloading. No push or deployment was performed.
