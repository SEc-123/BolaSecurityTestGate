# 0.6.8 local discovery decision budget candidate

The saved 0.6.7 Web retry `b4f6cfc5-4312-4ee1-9dee-658e3587e94f` discovered 50 endpoints and 10 features with zero failed tool invocations, then failed its `discover_target` task at exactly 20 model decisions with `iteration_limit_exceeded`. It did not produce a test matrix. That attempt is a failed acceptance run, even though the tools succeeded. This repair uses local fixtures only; it does not retry the saved Web target or any APK. Full Web and Android AI acceptance remain false.

## Finite task and run limits

Both serial and parallel schedulers previously imposed the same hard-coded 20-decision task limit. The parallel scheduler also divided the remaining run budget with `ceil`, so several workers could collectively exceed an explicit `max_steps`.

The runtime now resolves every task's allowance from the persisted scan configuration:

```json
{
  "agent_task_budgets": {
    "default": 20,
    "discover_target": 80
  }
}
```

These are keys inside `scan_config`, accepted by the existing scan creation API. `discover_target` applies when either the task intent or its legacy task type has that value. Discovery defaults to 80 decisions independently of the ordinary-task default, providing room for multi-page exploration and a final handoff. Ordinary tasks retain 20 decisions. Finite numeric overrides are rounded down and clamped to 1–200; omitted or invalid values use the corresponding default. Strings, booleans, null, NaN and infinity do not disable the bound. Model-authored task execution plans cannot increase it. Direct vulnerability expansion uses the same resolver.

The number counts model/planner decisions, including a completion, handoff or failure decision; it is not an HTTP request, discovered endpoint or browser-action limit. Existing tool failures, scope guards, provider refusals, cleanup and the two-correction selector limit continue to apply. A model call can still involve its own transport retries and timeouts; this change does not create a wall-clock deadline.

Each runtime invocation has a finite 10,000-decision default and upper bound. Explicit `max_steps` must be an integer from 1 to 10,000, and is validated before bootstrap or run mutation. A shared synchronous reservation counter limits actual decision attempts across all workers. Parallel batches claim no more tasks than the remaining allowance, and short tasks leave their unused allowance available to other workers. The final step count comes from reservations even if a worker rejects after consuming decisions. This also bounds repeated child-task creation within one invocation; a later explicitly started invocation receives a new run allowance.

A task that uses its full task allowance without completing fails with `iteration_limit_exceeded`. A task stopped by the shared run ceiling fails with `run_step_limit_exceeded`. If the shared allowance expires with unfinished work, the scan becomes failed with that phase and unstarted tasks become blocked. This preserves evidence and requires a new retry record, avoiding a scan that looks running after its worker exits. Finishing all work exactly at the cap remains successful; a genuine wait for user selection retains its existing semantics. Neither exhaustion path reports the stopped task as completed. `agent_task_budget` artifacts retain the effective task/run limits, and the model receives the current task allowance and remaining decisions so it can reserve a final handoff decision.

## Validation and packaging

The focused regression uses in-memory native SQLite, an explicit model-protocol server on loopback and one harmless registered tool fixture. It proves discovery can complete at decision 25 and release a dependent task in both scheduler modes, remains bounded at 80 decisions when it does not finish, honors configurable caps, and preserves exact explicit run limits under parallel contention. It also checks ordinary and legacy tasks, direct vulnerability expansion, unused-budget reuse, late worker rejection accounting and malformed values. It does not run a real model, browser or device.

The complete product experience suite additionally runs its existing local Chromium and loopback fixtures. Mobile closure uses its existing Appium/device doubles. These local tests do not establish real target, account, APK or Android device acceptance. Exact results, commands and the prior real Web failure are recorded in `validation/release-0.6.8.json`.

One full-suite run exposed a timing assumption in the existing HTTP event-stream disconnect test: it asserted server cleanup after a fixed 12 ms delay. The test now awaits the actual server close event with a five-second deadline. The event-stream implementation is unchanged, and the failed run is retained in validation history.

The normal frontend/backend build and release packaging workflow produces a local 0.6.8 candidate with a source manifest and SHA256 checksum. Installed dependencies are reused without downloads. Runtime databases, credentials, captures and local configuration are excluded from the package. This iteration is committed locally; no push, deployment or remote CI verification is claimed.
