# 0.6.10 local selector recovery candidate

The 0.6.9 discovery task failed after it had recovered from two selector rejections and completed ten further browser interactions. Safe invocation metadata supplied to this isolated repair shows the sequence: two completed interactions; `selector_ambiguous`; `selector_no_match`; ten completed interactions; a later `selector_ambiguous`. All three failures were `pre_action`, `action_performed:false`, `retryable:true`. The final failure was persisted as “Business UI action did not complete,” and its dependent task was blocked. The live run, target, account data, selectors, page contents and saved prompt were not accessed or changed by this repair.

## First broken contract

The browser adapter correctly rejected an ambiguous selector before dispatch and retained structured feedback. The agent runtime incremented `selectorCorrections` for each of the first two failures, but never reset the counter after successful interactions. Consequently, the third independent failure reached the terminal branch before another planner request could receive its correction feedback. This is an accounting defect in the runtime, rather than evidence that selector uniqueness or post-dispatch protection should change.

The regression recreates this ordering with native SQLite, real local Chromium and a loopback model-protocol fixture. It fails against the unchanged 0.6.9 runtime with a failed discovery task. With the fix, the same failed invocations remain persisted, the later failure reaches the next model request with its observed controls, its corrected unique click executes once, and the task completes.

## Bounded correction episodes

The runtime still permits only two correction decisions after consecutive recoverable pre-action failures. A successful selector-based `browser.interact` action (`click`, `fill`, `select`, `press` or `assert`) completes the correction episode and restores the allowance for a later independent failure. Successful observation, scrolling, navigation or unrelated tools do not restore it. This prevents a read-only or unrelated step from laundering a failing correction loop. The tool description explains this same contract to the model.

The original recovery scope remains discovery, generic vulnerability and upload tasks. The unchanged-action guard, exact selector uniqueness, readiness checks, cancellation, provider denial, scope restrictions and evidence gates remain enforced. A dispatched or uncertain action failure remains terminal with no automatic replay. The task and run decision budgets remain hard limits, including the default 80-decision discovery ceiling. A successful click still requires separate business-outcome verification.

## Visible uniqueness

A separate source-level mismatch was reproduced locally: the adapter promised exactly one visible match but counted hidden copies as ambiguity. The historical 0.6.6 contract and fixture explicitly retained this all-DOM behavior. The third live failure's two matches are not evidence that either was hidden; the repair does not make that claim.

The adapter now intersects the original locator with Playwright's `:visible` locator using `Locator.and`, available within the declared Playwright version range. That same live locator performs the count, visibility wait, readiness trial and actual action. This supports CSS unions and non-CSS selector engines without rewriting the selector or choosing a first/nth match. Two visible matches remain ambiguous. Zero visible matches are `selector_not_visible` when hidden DOM matches exist, and `selector_no_match` when the original selector has no matches. `match_count` reports the visible count.

Real Chromium regressions verify click/fill with hidden copies first and last; CSS, CSS unions, XPath, text and role selectors; two-visible and all-hidden rejections; and strict failure when another copy becomes visible between readiness and dispatch. The latter remains a terminal, uncertain-dispatch outcome with no replay. The existing ambiguity fixture now uses two visible controls, and the 0.6.6 document links to this superseding contract without rewriting its historical validation results.

## Verification and delivery limits

The new browser regression verifies the observed two-failures/ten-successes/later-failure sequence and confirms observation, scrolling and navigation cannot replenish an unsuccessful correction episode. Existing browser, readiness, model-context, task-budget, dependency and observed-request-gate regressions cover the remaining safety contracts. All 300 product tests, 202 mobile tests, 64 focused browser tests, typechecks and the normal build passed. Exact results are recorded in `validation/release-0.6.10.json`.

Two additional legacy static audits still fail on an outdated Chinese UI-string expectation and an exact page-list expectation. Both failures were reproduced from a temporary source archive of unchanged 0.6.9. They are recorded separately, not hidden or treated as passes; repairing those unrelated UI audit contracts is outside this browser correction. The aggregate mobile release gate includes actual device execution and was not run.

Only loopback browser/model fixtures were exercised. Mobile checks use device/Appium doubles; no Android runtime or real device was started. No dependencies were installed or downloaded. No live Web target or real model was replayed. Full AI Web and Android acceptance remain false, and the historical failed discovery task is not rewritten.

The normal packaging workflow produces the local 0.6.10 source/build archive with a source-tree manifest and SHA256. Runtime data, saved prompts, credentials and captures are excluded. The candidate is committed in its isolated worktree without push or deployment. Integration and a separately authorized live acceptance run remain outside this repair.
