# 0.6.13 local manual identity preparation candidate

Saved usernames and passwords previously reached the scan configuration, but login bootstrap existed only as a local planner suggestion. A model could complete discovery without calling it, after which role-sensitive tests ran with no scan-bound session. The task expander also treated the presence of account fields as proof that a session prerequisite was satisfied.

Web scans in manual account mode (`accounts` or the existing `identities` alias) now persist a dedicated login preparation task after discovery and before modeling/expansion. The scheduler attaches it as a prerequisite of generated tests and model-created test children. The preparation decision is deterministic; the model cannot skip the bootstrap call. Existing runs with pending tasks receive the same prerequisite on their next runtime entry. If discovery requests expansion early, the request becomes a persisted deferred expansion task; it runs deterministically after preparation so the workflow does not retain a stale missing-session plan.

The preparation task completes when its attempt and blockers have been persisted. It does not assert that all accounts authenticated or that a security test passed. The `account_auto_bootstrap_result` artifact retains `closed`, `partial`, or `blocked_needs_user_material`, with human-input requests for unresolved login material. Before native security test dispatch, the tool registry checks the preparation result and actual role-tagged account session material for this scan. BOLA needs attacker and victim sessions; BFLA needs attacker and privileged sessions; other authenticated tasks need the attacker session. An input override cannot weaken the task's original role requirement. Missing sessions block the test and leave the run failed with no security verdict.

Manual login reuses observed or supplied session material without registering accounts, changing roles, inventing credentials, truncating saved passwords, or repeating a recorded bootstrap attempt. Existing object fields remain intact. HTTP login must observe a changed session cookie or token as well as its success indication. A pre-login CSRF cookie is insufficient. OTP/MFA/captcha fields before or after submission produce a human-input blocker. The existing exact-origin HTTP scope guard remains in force; an out-of-scope login redirect is never followed. Public tests remain available when they do not require an account context. Android keeps its existing acquisition lifecycle.

Validation uses the real scheduler, registry, SQLite and loopback HTTP login server, with explicit planner protocol and final-analysis fixtures. It proves order, material propagation, dependency persistence, partial-role blocking, scope containment, and truthful product projection. It does not prove authentication on a particular live application, token freshness, MFA resolution, or business object ownership. JavaScript-only or custom login pages still need sessions observed by browser discovery or supplied by the operator; this change does not infer a new login API or expand authentication scope. Missing object IDs and native evidence remain subject to the existing workflow and finding gates.

The regression fails on clean 0.6.12 because no preparation task exists, and passes on this candidate. Exact commands, counts, and packaging limits are recorded in `validation/release-0.6.13.json`. No live target, saved account, actual model, APK or Android runtime was accessed by this repair; no service was restarted and no remote push was performed.
